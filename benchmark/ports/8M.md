# 8M · full-stack integration and repair

Five Luna/xhigh participants each use a separate wash Wasm guest. The DB,
backend, frontend, reviewer, and tester choose their shell commands within the
projected choreography. An API definition and the initial migration can run
independently. The backend can request another migration before its first
implementation. The current schema, API, implementations, and reviews become
the inputs of the actual integration test.

A negative integration result goes to the reviewer. The reviewer submits the
chosen correction through the typed write-only repair file. The global enables
the corresponding branch. Each developer's existing outcome file delivers the
actual failed test and the accepted repair choice. The EPF and effect auditor
checks their correspondence against the actual decision receive, test effect,
and next candidate. A compatible UI approval can be reused after a backend-only
repair. A schema or API change requires matching new downstream evidence.

The actual-Wasm boundary test covers an early migration, a rejected backend
review, and successive backend, schema, and API changes after failed tests.
Three developers can begin blocking reads before the reviewer has submitted the
choice. The 24 effects and 8,877 complete observations pass the common score,
EPF and effect audit with zero violations. The ordinary WASI qualification
command includes this test.

The three live pilots use one runtime and wash binary and `common-environment-v27`.
