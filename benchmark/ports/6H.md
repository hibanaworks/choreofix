while B and C prepare. B's integration follows A's successful stage and the
B/C preparation join; C follows B's successful stage. This is the declared
partial order, not arbitrary merge or deployment pipelining.

staging have explicit repair continuations. Staging failure includes an actual
rollback before a fresh implementation/test/review/merge cycle.

Repository, test, review, CI and staging localsides drive the actual Endpoints.
Each operation file is bound directly to its request and actual response.
There is no extra merge-ready notification: developers submit the actual merge
request and the global enforces its prerequisites. The build server sends its
actual positive CI/publication context directly to staging. The staging owner
notifies the other native participants after the final successful validation.

The staging localside receives the actual STAGING_ENV Endpoint once. File
requests reach that Endpoint directly. Before deployment it checks the exact
positive CI/publication data and the actual validated preceding service.
After validation it sends the typed positive/negative outcome. A negative
outcome requires the original service's rollback request and checks that the
actual removed deployment is the one just rejected. Stored values are real
material and validation receipts, not progress flags or a holder table.
