# 12M: equipment-dependent ingredient preparation

Status: not migrated or qualified. The direct boundary remains qualified for
18/48 tasks; this task does not increase that count. The earlier 12E binary,
51 Wasm conditions and live pilot are not 12M evidence.

The authoritative common world is `benchmark/environments/12M/sim.py`, using
`KitchenSim`. Ingredient resource requirements come from the actual ingredient
configuration, rather than the empty default `prepare_ingredient` metadata.
The same requirements apply to every compared method.

| Actual operation | Physical Endpoints required |
| --- | --- |
| A: appetizer base | OVEN and STOVETOP |
| B: main-course base | OVEN and STOVETOP |
| C: dessert base | OVEN |
| A: sauce for C | STOVETOP |
| B: garnish for A | STOVETOP |
| C: glaze for B | OVEN |

Each combination consumes its own completed base and the completed incoming
ingredient: garnish for A, glaze for B, sauce for C. It must not wait for an
unrelated chef's work or for its own outgoing ingredient. The source must
preserve those three independent completion boundaries.

The direct operation files retain 12E's actual-file/Endpoint binding and real
request/result path. Ingredient preparation additionally needs actual equipment
loans, resource requests, results and returns in the same global. Copying the
12E ingredient receiver would bypass that required boundary.

A and B's base effects exclude every other equipment effect while holding
both Endpoints. A stove-only ingredient and an oven-only base/ingredient can
overlap. Serializing all six operations, bundling the two resources for every
ingredient or prescribing a shell recipe would lose that independence and is
not the intended port. Unread file results must not retain returned equipment.

There are 24 orders of the four oven operations and 24 orders of the four stove
operations. Their relative A/B base order must agree, yielding 288 compatible
pairs of resource orders. This is a source-design count, not 288 completed
tests or an assumption that all such schedules have been implemented. Simply
putting both resource order trees in `par` also admits incompatible pairs and
does not establish a correct source.

An alternative naive six-operation permutation trie has 1,956 operation nodes.
With the direct request/loan/resource/result/return/material paths, its
operation-body count alone would be about 15,322 events before bootstrap,
metadata, shutdown and choice markers. This estimates that particular
duplicated encoding; it is not a lower bound on a correct choreography or an
executed compiler benchmark. The current global image's 65,535-byte bound must
not be bypassed or its const evaluation lint suppressed.

The source design and direct localsides remain unfinished. No application
holder table, progress flag, allocation callback, host-selected order or
second resource arbiter is authorized as a substitute. Qualification still
requires actual Wasm schedules with both resource orders, genuine disjoint
equipment overlap, early per-dish completion, recoverable invalid requests,
complete EPF, exact request/effect/result checks, neutral common scoring and a
source-bound real-agent run.
